# 离线信封登录（替代在聊天里发账号密码）

> 信封只承载 **Bambu 账号 + 密码**。凭据由本机主密钥 `host-key.bin` 保管，不需要任何安全码，
> 理由见下面「为什么没有安全码」。

## 为什么要改

旧流程里三件事都必须把秘密**打进 QQ 聊天**：

```
/打印机 登录 <Bambu账号> <密码>     ← 账号密码进聊天记录

```

聊天记录是明文留存的（QQ 服务器、群管理、任何能看历史的人、备份、同步盘）。
撤回不可靠。所以把这三条**整体替换**成一条：

```
/打印机 登录              → 机器人回一个 GitHub Pages 链接
<点开链接，在网页里填，网页本地加密>  → 得到一段 BBX1.xxxx 文本
/打印机 登录 BBX1.xxxx    → 机器人解信封、登录、拿到 token
```

秘密只在两个地方以明文出现：用户的浏览器内存、模块进程内存。**不经过聊天、不落盘、不进日志。**

细节见 [ENVELOPE.md](ENVELOPE.md)（信封二进制格式）。

## 密钥

- 私钥 `bbx-key.json`：`api.dataDir()` 下，0600，首次用到时生成，之后复用。**永不导出、永不进聊天/面板/日志。**
- 公钥：87 字符 base64url，写进出给用户的链接的 hash 里（`#k=...`，hash 不会发给 GitHub，也不会进服务器日志）。
- 设置里点「重置密钥」→ 换一把新私钥，旧链接立即作废（已经在途的信封也解不开）。这是「疑似泄露」时的应急手段。

## 推荐地址从哪来

设置项 `enrollBaseUrl`（文本）：

| 值 | 效果 |
|---|---|
| 留空 | 用模块内置的默认地址（见 `lib/envelope.mjs` 的 `DEFAULT_ENROLL_BASE`） |
| `https://<用户名>.github.io/<仓库>/` | 用你 fork 后自己部署的那份（推荐：别人改不了你的页面） |
| 任何 http(s) 绝对地址 | 照用，机器人只把 `#k=<公钥>` 拼上去 |

机器人只校验它是 `http://` 或 `https://` 开头、长度 < 300；**不会**去请求它。

## 命令（全部只允许私聊）

| 命令 | 作用 |
|---|---|
| `/打印机 登录` | 没带参数 → 回登录链接（含公钥）+ 怎么用。**不要求已解锁**（新用户正是来建号的）。 |
| `/打印机 登录 <信封>` | 解信封并按内容做三件事之一（见下）。 |
| `/打印机 验证码` / `/打印机 验证码 <6位>` | 云端要验证码时：先请求发送，再提交。 |
| `/打印机 两步验证 <6位>` | 两步验证。 |

### 为什么没有安全码

信封私钥（`bbx-key.json`）与 `vault.json` 在**同一个数据目录**里：能读目录的人本来就能同时拿到两者，
所以「每人一个安全码」对这类人不提供额外保护，只留下「忘了就永久丢数据」和「每次都要输」的成本。
现在 DEK 由本机主密钥 `host-key.bin` 直接包着，每人仍是一把独立 DEK。

代价：**能读数据目录的人可以解开所有人的凭据**。这台机器本身必须是可信的。

**已删除**：`/打印机 设置安全码 <密码>`、`/打印机 解锁 <安全码>`、`/打印机 改安全码 <旧> <新>`、
`/打印机 登录 <账号> <密码>`。旧写法仍能识别，但一律拒绝并回「改用登录链接」——
不能让「有人照着旧帮助发一句明文」继续存在。

## 一个信封，一种用途

**登录**：账号 + 密码。解出来之后建号（如果还没有）→ 登录云端 → token 加密落盘。

约束：

- `exp` 过了（含 120 秒时钟偏移）→ `EXPIRED`；
- `jti` 用过 → `REPLAYED`（先记账再执行，失败的也作废）；
- `ttlMin` 超过设置 `enrollMaxTtlMinutes` → `BAD_PAYLOAD`。

## 面板接口

路径同样在 `/aurabot/api/ext/bambu-print/` 下。

### GET /enroll

> **关于 `open()` 返回明文**：信封服务**必须**把账号 / 密码交给装配层（`index.mjs`）去登录云端和
> 云端登录，所以 `open()` 的返回值里有这些字段。这是唯一允许出现明文的地方，范围就是那一个函数栈：
> 它不进 `inspect()`、不进日志、不进审计 note、不进任何路由的响应、不写盘。
> `index.mjs` 的 `applyEnvelope()` 在 `finally` 里把字段置空。

```json
{
  "ok": true,
  "link": "https://xxx.github.io/enroll/#k=<87 字符公钥>",
  "publicKey": "<87 字符>",
  "baseUrl": "…实际用的前缀…",
  "custom": false,
  "fingerprint": "a1b2c3d4",
  "ttlMinutes": 60,
  "maxTtlMinutes": 1440,
  "keyCreatedAt": 0,
  "stats": { "used": 0 }
}
```

`fingerprint` = SHA-256(公钥原始 65 字节) 前 4 字节的 hex（8 位），方便口头核对「网页上显示的和机器人说的是同一把」。
  `keyCreatedAt` 是毫秒时间戳。
**不含私钥**，也永不含私钥。

### POST /enroll/rotate

`{ confirm: true }` → `{ ok:true, link, publicKey, fingerprint }`。换新私钥、清空已用 jti。
必须主人、且必须已解锁（`LOCKED` / `OWNER_ONLY`）。

### POST /enroll/inspect

`{ text }` → 只**解信封并回显元数据**，不执行任何动作：
`{ ok:true, kind:'login', ttlMin, expiresAt, region, accountMasked, hasPassword }`。
面板用它做「贴进来先看看对不对」，**不回显密码/账号明文**（账号用 `a***@b.com` 这种掩码）。

### 设置项

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `enrollBaseUrl` | text | `''` | 登录网页前缀；留空用内置默认 |
| `enrollTtlMinutes` | int | 60 | 生成的链接/示例信封建议生存时间，1~1440 |
| `enrollMaxTtlMinutes` | int | 1440 | 服务端接受的最大生存时间，1~1440；超出 `BAD_PAYLOAD` |

## 静态网页

`assets/enroll/` 原样发布到 GitHub Pages（任意静态托管也行）。**没有构建步骤、没有依赖、不发任何网络请求。**

| 文件 | 作用 |
|---|---|
| `index.html` | 唯一页面 |
| `bbx.js` | 信封加解密唯一实现（浏览器 + Node 共用，互操作测试靠它） |
| `enroll-form.js` | 表单校验 / 组装 payload（纯函数，可在 Node 测） |
| `style.css` | 样式 |

页面从 `location.hash` 的 `#k=` 取公钥；没有就显示「先用 /打印机 登录 拿链接」并允许手动粘贴公钥。
生成后只给一段文本 + 复制按钮，反复强调「只在私聊发、发完删掉」。

## 为什么这比「把秘密发聊天」真的更安全

| 威胁 | 旧流程 | 信封 |
|---|---|---|
| QQ 服务器 / 备份 / 同步盘读到历史 | 直接拿到账号密码 | 只有密文；没有本机私钥解不开 |
| 群管理员翻群历史 | 同上（群里被直接拒绝，但私聊仍留存） | 同上 |
| 机器人管理员（主人）看别人密码 | 看不到了（本来就看不到），但能看到聊天里的明文 | 信封里连主人也解不出**别人**的密码——私钥只解「投递给这台机器的那一次」 |
| 事后翻旧消息重放 | 直接重发一遍就能登录 | `jti` 一次性 + `exp` 过期，重放是 `REPLAYED` |
| 静态网页被别人 fork 改坏 | — | 改页面只能偷到用户输入（那本来就该输），**偷不到私钥**；认准 hash 里的公钥指纹即可 |

## 私钥放在哪，以及这条威胁模型到底挡什么

「能读数据目录的人」是一个真实威胁，但它有三种强度，**解法完全不同**。逐一说明：

### 强度 A：事后拿到数据目录（备份、同步盘、被拷走的磁盘、离职后的整机）

**可解，默认已解一半。** 设置项 `enrollKeyMode`：

| 值 | 私钥在哪 | 重启后旧链接 | 事后拿到数据目录能解开在途信封吗 |
|---|---|---|---|
| `file`（默认） | `bbx-key.json`（0600） | 仍然有效 | **能** —— 这是默认值的已知代价 |
| `ephemeral` | **只在进程内存**，磁盘上没有任何副本 | 失效，要重新拿 | **不能**：数据目录里只有公钥；进程一停私钥就没了 |

`ephemeral` 模式下模块**既不读也不写** `bbx-key.json`，而且启动时会**删掉**上一任留下的那份
（删不掉就报 `IO` 并拒绝启动 —— 不能让用户以为磁盘上已经干净了）。

为什么必须删而不是「留着不用」：旧钥对应的公钥可能还印在用户手里的旧链接上，
用户完全可能用旧链接生成一段新信封发过来（本模块会拒收 `BAD_TAG`），
但**那段密文已经躺在聊天记录里了**；事后拿到数据目录的人用那把残留旧钥就能解开它。
只删不用，才能让「磁盘上没有私钥」这句话成立。

代价是重启（含模块热重载）后旧链接失效，用户要重新发一次 `/打印机 登录` —— 一条命令的事。

### 强度 B：机器人**运行期间** dump 进程内存 / 调试器attach

**明确不解决，也不可能在这个架构里解决。** 私钥必须在内存里才能解密；能读进程内存的代码
已经能拿到同一进程里的 vault DEK、云端 token、以及所有明文 —— 信封不是短板，进程边界才是。
报告里应该写清楚：**这是「这台机器本身可信」的前提**。

### 强度 C：能改这个模块的代码（本机管理员主动作恶）

**明确不解决。** 改了代码就能在解密那一刻把明文抄走。任何「本机运行、本机解密」的方案都一样。
唯一解法是换一台干净机器，或用硬件密钥（下面「还能走到哪一步」）。

### 为什么仍然值得做

因为它把损坏的**持久性**改掉了：

| | 旧流程 | 信封 |
|---|---|---|
| 泄露的东西 | 账号密码**明文** | 一段密文 |
| 留在哪 | QQ 聊天记录（服务器、群管理、备份、多年历史） | 聊天里只有密文 |
| 有效多久 | **永久**，改了密码才算完 | 到 `exp` 为止（默认 60 分钟），且用一次就作废 |
| 谁能解 | 任何看到记录的人 | 只有这台机器，且只在那个时间窗口内 |

所以哪怕强度 B/C 成立，攻击者能拿到的也是「一段几十秒到一小时内的在途信封」，
而不是「这个人 2019 年发在群里的账号密码」。

### 能不能把私钥托管到 GitHub？

**不能作为「更安全」的方案，只能当「换一个信任对象」。** 逐个说清楚为什么：

#### 1. GitHub Secrets 不是密钥托管

`Settings → Secrets → Actions` 里的 secret：

- **同一仓库的写权限持有者可以读。** 管理员改一个 workflow 就能把 secret 打到日志或外发 —— GitHub 自己写明
  "secrets should be treated as accessible to anyone who can modify workflows"。
  也就是说，把私钥放进 Secrets，等于把它交给了**所有对这个仓库有写权限的人**（协作者、组织管理员、
  被授予权限的 bot、乃至将来接手的人）。
- **模块运行时读不到它。** Secrets 只在 Actions 运行时以环境变量/文件形式注入，本地 Node 进程没有任何
  GitHub API 能取回 secret（设计如此，没有「读 secret」的接口）。
  所以「模块启动时从 GitHub 拉私钥」这条路**在 API 层面就不存在**。

结论：把它放进 GitHub **没有减少**任何威胁，反而多了「仓库协作者」这一类人。

#### 2. 放进公开仓库

直接等于公开私钥。任何人 clone 就能解开所有在途信封，而且因为仓库有历史，**删掉也不作数**。
这是绝对禁止项，本模块也不会提供任何「从 URL 拉私钥」的选项。

#### 3. 放进私有仓库 + 只读 token

理论上：私有仓库 + 一个只读 token，模块启动时 GET 这个文件。但：

- 只读 token 本身必须存在于本机（配置/环境变量），**攻击者拿到它就能读同一份私钥** —— 没有变安全，
  只是把「一把私钥」换成了「一把私钥 + 一个 token」；
- 每次启动都要联网，GitHub 一抖动登录信封就全挂；
- 引入了新的出站请求与新的失败模式，与本模块「只连必要地址」的约定冲突。

#### 4. Actions 里做加解密（把 GitHub 当解密机）

即「网页把密文发给 Actions，Actions 解完再送回来」。这等于把私钥交给 GitHub 的 runner：

- runner 是 GitHub 的机器，私钥在它的内存里，且它的镜像与日志你无法完全审计；
- 每个跑 workflow 的人都能改那一步把明文吞掉；
- 明文还要再经一次网络传输才能到机器人 —— **比现在多了两个信任点**。

### 那么「托管到别处」正确的做法是什么

**让私钥离开数据目录，但仍然是本机文件。** 本模块支持 `enrollKeyPath`（绝对路径），
配合操作系统/编排层自己的 secret 机制：

| 做法 | 谁保护私钥 | 本机进程还读得到吗 | 适用 |
|---|---|---|---|
| 默认 `bbx-key.json`（数据目录） | 文件权限 0600 | 能 | 单人机器、能接受「备份里有私钥」 |
| `enrollKeyMode=ephemeral` | 只在内存 | 能（本来就要用） | **推荐**：磁盘上根本没有私钥 |
| `enrollKeyPath` → 加密卷 / 独立分区 | 卷的加密口令 | 能（挂载后） | 磁盘整体被拷走时不泄露 |
| `enrollKeyPath` → systemd credentials / 容器 secret 挂载 | 宿主的 secret 管理 | 能 | 服务器部署，secret 不进镜像与备份 |
| `enrollKeyPath` → Vault / KMS 注入的文件 | 集中式 secret 管理 + 审计 | 能（注入后） | 多机统一治理，能回答「谁在什么时候取过」 |

关键点：**这些方案都没有让私钥离开「本机进程能读到」的范围**，因为解密必须在本机发生。
它们做的是「缩小磁盘上那份副本的暴露面 + 让取用可审计」。

真正的下一步只有硬件密钥（私钥不可导出，解密在 TPM/安全芯片里）——
Node 没有跨平台 API，需要原生插件，与本模块「只用内置模块」的约束冲突；要做得单独立项。

### 还能走到哪一步（未实现，按需）

真要挡强度 C，只有把私钥移出这台机器：

1. **硬件密钥 / TPM / Secure Enclave**：私钥不可导出，解密必须经过硬件。
   Node 没有跨平台标准 API，要写原生插件 —— 与本模块「只用内置模块」的约束冲突。
2. **外部解密服务**：把私钥放在另一台机器/手机上（比如用户在手机上装个页面离线解密），
   机器人只负责转发密文。可行，但要多维护一个组件，且用户在网页上填的东西仍然要经过那台手机。
3. **一次一密 + 人工带外确认**：机器人给一段一次性口令，用户按口令在网页上算，
   机器人只显示校验值。彻底不上传任何东西，但用户体验差很多。

这三条都超出「在现有模块里补一刀」的范围，先记在这里。
